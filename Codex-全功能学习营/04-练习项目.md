# 04｜完整演练：一次小而完整的交付

选择一个不涉及生产数据的小需求，例如“为页面增加一个清晰的空状态”。按以下顺序在 Codex 中完成。

## 第一步：探索

```text
只读分析：为了实现 <需求>，请找出相关页面、数据来源、现有测试和类似 UI。给我一个最小改动计划与风险；不要修改文件。
```

## 第二步：确认计划

检查它是否写清：修改哪些文件、不会修改哪些文件、如何验证。若不清楚，追问“为什么要改这个文件？”或“能否复用现有组件？”

## 第三步：实施

```text
按刚才确认的最小计划实施 <需求>。保持现有风格与 API 不变；补充覆盖 <边界情况> 的测试。完成后运行最相关的检查，不要提交或推送。
```

## 第四步：验证与审查

```text
审查你刚完成的改动：重点检查空数据、加载失败、可访问性和无关改动。报告发现；如没有问题，说明已运行和未运行的验证。
```

## 第五步：交付

自己查看 Diff 和测试输出。满意后才发：

```text
总结本次改动、验证结果和仍需人工验证的项目。建议一个符合本项目风格的 Git 提交信息；不要执行提交。
```

## 复盘问题

1. 我的验收条件是否可观察、可测试？
2. Codex 的信息是否来自实际文件，而非猜测？
3. 改动是否足够小且没有覆盖我的其他工作？
4. 哪个验证失败或未运行，原因和影响是什么？
5. 下次我会补充哪一种上下文？

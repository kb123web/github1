# 03｜协作与定制：把 Codex 接入你的工作流

## Git 协作

- 先让 Codex查看 `git status` 和当前分支；它不应覆盖你已有的无关改动。
- 提交前要求：检查 Diff、运行约定验证、用清晰的提交说明概括“为什么”。
- 推送、创建 PR、合并和任何生产操作都属于外部影响操作：确认目标仓库、分支和内容。

示例：

```text
检查当前 Git 改动，只审查与 <功能> 有关的文件。告诉我建议提交哪些文件、应运行哪些验证；不要暂存、提交或推送。
```

## 图片、文档、表格与演示文稿

在桌面版可上传这些材料作为任务上下文。描述你希望提取、修改或生成的结果，并指定输出格式和验证方式。例如：

```text
阅读这份需求文档，提取可开发的功能清单和验收条件。不要臆测未写明的规则；把不确定项列成问题。
```

对 `.docx`、PDF、表格、幻灯片等“视觉布局重要”的成品，要求 Codex 渲染检查后再交付。若要新建图片，请描述主体、风格、尺寸、背景和用途。

## Skills（技能）

技能是可复用的专门工作流，例如生成文档、处理表格或创建插件。需要时直接说“使用 <技能名> 做 <任务>”；Codex 会读取该技能的说明并按其中流程执行。它适合重复且有明确质量步骤的工作，不适合塞进每一个小问题。

## MCP 与连接器

MCP 服务器/应用连接器把 Codex 接到你已授权的外部系统（如代码托管、文档、日历或内部服务）。连接前确认：数据范围、读写权限、令牌归属和组织策略。连接器是访问私有数据的正确渠道；不要把私有资料复制到公开搜索中。

## 持久化定制

| 需求 | 合适位置 |
|---|---|
| 当前任务的临时要求 | 当前对话 |
| 仓库的编码规范、命令、验收规则 | `AGENTS.md` |
| 受信任项目的工具/沙盒/MCP/模型默认项 | `.codex/config.toml` |
| 可复用的专业流程 | Skill |
| 可安装的一组工具、技能和配置 | Plugin |
| 定时提醒、巡检和持续跟进 | Automation |
| 生命周期或工具调用的机械约束 | Hook |

不要把一次性要求写进长期规则，也不要把秘密写进 `AGENTS.md`、配置或提交记录。

## 自动化与浏览器/计算机操作

如果你的版本提供自动化，可创建提醒、周期巡检或“完成后通知”的任务。描述触发频率、检查对象、什么情况需要通知；状态未变化时通常应保持安静。浏览器测试或计算机操作应限定站点、账号和允许动作，涉及发布、支付、删除、发送消息时必须让人最终确认。

## 本节练习

```text
为这个仓库草拟一份 AGENTS.md 建议内容，但先不要写文件。它应包含：项目概述、常用验证命令、改动原则和提交前检查。每一条都要说明来自哪个现有文件或为什么仍需人工确认。
```

# 02｜让 Codex 写代码：从问题到验证

## 四种高频任务

### 1. 新功能

先让它找相似实现，再最小化实现：

```text
先找出项目中最接近 <功能> 的实现并说明复用方案。确认后再实现；不要重构无关代码。完成后运行相关测试。
```

### 2. Bug 调试

提供可复现证据：

```text
Bug：<现象>。
复现：1. ... 2. ...；期望：...；实际：...。
请先定位根因并指出证据，随后做最小修复，增加能防回归的测试，并运行它。
```

### 3. 重构

把“不改变什么”写清：

```text
将 <模块> 拆分为更清晰的职责，但保持公开 API、页面行为和数据格式不变。先提出文件级计划；实施后跑类型检查和测试。
```

### 4. 代码审查

审查默认不等于修改：

```text
只审查当前改动，不编辑文件。按严重程度列出可复现的问题；每项要包含文件、位置、原因和建议。没有问题请明确说明。
```

## 验证清单

- 单元/集成测试是否覆盖新行为和边界？
- 静态检查、类型检查、构建是否与项目约定一致？
- 是否手工验证了关键用户路径？
- 命令未能运行时，原因是什么，哪些结论因此不成立？
- 是否混入格式化、重命名、依赖升级等无关改动？

## 调试的好习惯

不要只说“修一下”。给出日志、请求与响应（去除密钥）、触发条件、最近改动和正确行为。要求先解释根因，可以防止“碰巧不报错”的修复。

## 本节练习

选一个微小改动，发送：

```text
为 README 增加一段“本地启动”说明。先确认真实启动命令来自哪里；只修改 README；完成后检查 Markdown 链接和格式。
```

然后在 Diff 中逐行查看，练习让 Codex 根据你的反馈做一次小修订。

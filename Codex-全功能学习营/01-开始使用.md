# 01｜开始使用：把需求交给 Codex

## 最小工作循环

1. 给出目标、范围和验收标准。
2. 允许 Codex 先查看相关文件并说明发现。
3. 要求它实施、运行恰当的验证，并报告改动与剩余风险。
4. 在 Diff 中复核，再决定是否提交。

好的首次请求：

```text
请先阅读 README 和项目结构，不修改文件。用不超过 8 条说明：项目用途、启动方式、测试方式、主要入口，以及你发现的风险或缺失信息。
```

接着：

```text
在不改变现有接口的前提下，为 <功能> 实现 <行为>。
验收：<具体表现>；请补充或更新测试，运行 <命令>，最后列出改动文件和未验证项。
```

## 信息要素

| 要素 | 示例 |
|---|---|
| 目标 | “用户可按日期筛选订单” |
| 范围 | “只改前端订单页，不改后端” |
| 约束 | “沿用现有组件库、中文文案、不能新增依赖” |
| 验收 | “空结果有提示；已有测试通过” |
| 参考 | “遵循 `src/pages/Users.tsx` 的筛选样式” |

## 读、改、运行的区别

- **只读探索**：让 Codex定位文件、解释逻辑、评估方案；适合先理解陌生项目。
- **编辑实现**：明确授权它修改工作区内文件；改动后应要求它验证。
- **运行命令**：构建、测试、安装依赖或启动服务可能耗时、联网或改变本机状态。看清命令与影响再批准。

## 上下文管理

- 用文件路径、报错全文、截图和复现步骤代替“这里坏了”。
- 一个线程专注一个主题；新需求会改变原目标时，开新线程避免混淆。
- 需要长期团队规则时写入仓库 `AGENTS.md`；一次性的偏好只写在当前对话。
- 让 Codex 先复述它理解的范围，特别适合涉及迁移、权限、资金或数据的任务。

## 本节练习

```text
仅做只读分析：查看当前仓库，告诉我如何启动、如何测试、有哪些未追踪文件。不要修改、安装或执行网络命令。
```

通过标准：你能看懂它引用的文件和它建议的下一步。
